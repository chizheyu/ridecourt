Read CODEBUDDY.md and docs/SPEC.md first. Do build-order step 1 only (no LLM code yet).

1. requirements.txt (fastapi, uvicorn[standard], pydantic>=2, google-genai, httpx, pytest), a virtualenv in .venv, install it. Add .gitignore (.venv, __pycache__, .env, devlog/*.stderr.log).
2. Package `ridecourt/` with `__init__.py`.
3. `data/policy.md`: the full policy with clauses P-RD-1, P-RD-2, P-NS-1, P-NS-2, P-FA-1, P-SF-1, P-BF-1 as in SPEC section 5, each with a one-line rationale. Agents will cite these IDs.
4. `ridecourt/policy.py`: pure functions, one per clause, and `evaluate(dispute, trip, profiles, facts) -> PolicyResult(applicable_clauses, outcome, amount, computation)`. `facts` are numbers computed by tools: distance_actual_km, distance_optimal_km, duration_actual_min, duration_optimal_min, rider_requested_change, road_closure, min_distance_to_pickup_m, wait_minutes_past_eta, contact_attempts, recomputed_fare, charged_total, promo_valid_at_booking. Route deviation refund = (extra km x per_km + extra minutes x per_min) x surge_multiplier, rounded to cents. Driver no-show = cancellation fee refunded + S$3 credit. Fare error = the difference. Safety = outcome "escalate", amount 0. `computation` is a human-readable string showing the arithmetic.
5. `ridecourt/tools.py`: for now only `compute_facts(trip, chats)` with what the policy needs (haversine distances, wait time, contact attempts, fare recompute, requested-change and road-closure detection from chat text with simple keyword rules). Step 2 will expand the tools.
6. `scripts/generate_data.py --seed 7` writes `data/synthetic/`: trips.json, chats.json, profiles.json, disputes.json, precedents.json (12 past rulings), per SPEC section 4: about 48 disputes in the stated mix, real Singapore coordinates, GPS points every 15 s with speed, optimal routes, Singapore-like fares (base about S$3, about S$0.75/km, about S$0.25/min, booking fee S$1, surge 1.0 to 1.8, cancellation fee S$4), realistic chat lines (requested stops, road closure notes, contact attempts, threatening language in safety cases), call attempts, rider and driver profiles including two bad-faith patterns. Labels go in a separate `data/synthetic/labels.json` computed with the policy engine, so agents never see them.
7. `ridecourt/data.py`: pydantic models and a loader for this dataset, with an adapter interface so the organiser's sample dataset can be plugged in later.
8. Tests: `tests/test_policy.py` (every clause, with edge cases: exactly 15 percent, requested stop, road closure, 149 m vs 151 m, 4.9 vs 5.0 minutes, valid vs invalid promo, safety always escalates) and `tests/test_data.py` (dataset loads, counts per category, every dispute has a label).

Run `.venv/bin/python -m pytest -q` until it passes. Commit. Finish with a short summary of files, test count, and anything you changed from the spec.
