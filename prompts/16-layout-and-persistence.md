Read CODEBUDDY.md and docs/SPEC.md. Recording the demo on the live app found two problems that a judge trying the app will hit.

1. The evidence list disappears next to a ruled case. Since step 14 the ruling card (outcome, computation, citations, markers, reasoning, two messages, buttons) fills the evidence panel: in a 1440x810 window the evidence list shrinks to one partly visible line, and even at 1920x1080 only one line shows for a no-show case, so clicking a citation chip shows almost nothing. Rework the right-hand panel so that at 1440x810 and at 1920x1080 a reviewer can see the ruling's outcome and amount and at least three evidence items at the same time, and clicking any E# chip (in the courtroom or on the card) brings that evidence item into view and highlights it. For example, keep the outcome, amount, confidence and markers always visible and let the reasoning and the two messages expand on click, or give the evidence list and the ruling card their own scroll areas with a minimum height. Keep the layout working at 1024 px wide. Add a test in the style of the existing UI tests for what you can check without a browser, and describe in your summary what a person should see at each window size.

2. All state lives in memory, so it is lost whenever the Cloud Run instance restarts (it did at about 14:30 today). A judge who opens the app later sees every case as new, waits for each live resolve, and never sees a precedent learned from an override. Add a persistence layer:
   - A store interface with two implementations: in-memory (default; used by the tests and for local runs) and Firestore (`STATE_BACKEND=firestore`; the project's default Firestore database in native mode, asia-southeast1). Use collection names prefixed with `ridecourt_` because another app uses the same database.
   - Persist case files including their events, case statuses, human overrides and the precedents learned from them, and the daily resolve counter (the cost guard must not reset when the instance restarts). The per-visitor hourly limit can stay in memory.
   - The live app must show cases that another process wrote to the store without a restart (read through to the store when a case is not in memory, with a short cache for the queue).
   - Add `scripts/preresolve.py`: resolves every labelled case (or a given list) in the current process with the configured LLM and writes the results to the configured store, one case at a time, skipping cases already resolved unless `--force`. It prints one progress line per case and continues after a failed case.
   - Add a "Run again" button on a resolved case that re-runs it live (it counts toward the cost guard) and replaces the stored result when the new run finishes; the timeline shows the new run as it streams.
   - Firestore documents are limited to 1 MB: check the largest case file and store events in a way that stays under the limit.
   - Tests with a fake store: state survives creating a new app instance on the same store (a resolved case, an override and its learned precedent, the daily counter); a case written by another process appears in the queue; preresolve skips done cases.
   - `scripts/deploy.sh`: set `STATE_BACKEND=firestore` and grant the service account `roles/datastore.user` on the project, with the same retry loop as the existing IAM binding. Document the setup in the README.

Do not run real Gemini and do not run preresolve against Firestore (a full evaluation is running and shares the model quota; the reviewer will run preresolve after deploying). Commit and summarize.
